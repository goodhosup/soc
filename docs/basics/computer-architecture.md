# 컴퓨터 구조 기초

!!! spec "규격 · 세대"
    명령어 집합 아키텍처(ISA): Arm A64(Armv8-A 이후), x86-64, RISC-V · 관련 개념: 파이프라인, 슈퍼스칼라, 비순차(Out-of-Order) 실행, SIMD(Arm NEON·SVE2)
    단순 순차 파이프라인(초기 ARM, Cortex-A7·A53 계열) → 비순차 실행 모바일 코어(Cortex-A9 이후) → 넓은 디코드·대형 ROB 코어(Apple 자체 코어, Cortex-X 계열)

!!! basic "한눈에 보기"
    CPU는 **명령어**를 하나씩 읽어 실행하는 기계입니다. 성능을 올리는 방법은 크게 세 가지입니다.

    1. **클럭을 높인다** — 1초에 더 많은 박자를 친다. 하지만 전력과 발열이 급격히 늘어납니다.
    2. **한 박자에 더 많은 명령을 처리한다(IPC를 높인다)** — 여러 명령을 동시에, 순서를 바꿔 가며 처리합니다.
    3. **한 명령으로 더 많은 데이터를 처리한다** — 같은 연산을 여러 데이터에 한꺼번에 적용합니다(SIMD).

    식당 주방에 비유하면 1은 요리사가 더 빨리 움직이는 것, 2는 요리사를 늘리고 재료 손질·굽기·담기를 나눠 동시에 하는 것, 3은 한 번에 여러 접시를 같이 만드는 것입니다.

    **성능 = 클럭 × IPC**라는 관계가 이 책 CPU 장 전체의 출발점입니다.

## 명령어 집합 (ISA) { .l2 }

명령어 집합은 "CPU가 알아듣는 말"의 사전입니다. 같은 ISA를 쓰면 같은 프로그램이 돌아가고, 그 아래 회로(마이크로아키텍처)는 회사마다 다르게 만들 수 있습니다.

| 구분 | RISC 계열 (Arm, RISC-V) | CISC 계열 (x86) |
|---|---|---|
| 명령 길이 | 고정 길이(A64는 32비트) | 가변 길이(1–15바이트) |
| 메모리 접근 | 로드·스토어 명령만 메모리 접근 | 연산 명령이 메모리를 직접 피연산자로 씀 |
| 디코드 | 단순, 넓게 병렬 디코드하기 쉬움 | 복잡, 내부적으로 마이크로 연산으로 쪼갬 |
| 레지스터 | A64: 범용 31개 | x86-64: 범용 16개 (최신 확장으로 32개) |

현대 고성능 코어는 어느 ISA든 내부에서 명령을 **마이크로 연산(µop)**으로 바꿔 처리하므로, ISA 차이보다 마이크로아키텍처 차이가 성능을 더 크게 좌우합니다. 다만 고정 길이 명령은 디코더를 넓게 만들기 쉽다는 실질적 이점이 있습니다.

## 파이프라인과 슈퍼스칼라 { .l2 }

```mermaid
flowchart LR
    F["Fetch<br/>명령 가져오기"] --> D["Decode<br/>해석"]
    D --> R["Rename<br/>레지스터 이름 바꾸기"]
    R --> I["Issue<br/>실행 유닛에 보내기"]
    I --> E["Execute<br/>ALU · 로드/스토어 · FP/SIMD"]
    E --> C["Commit<br/>순서대로 결과 확정"]
```

| 기법 | 아이디어 | 한계 |
|---|---|---|
| 파이프라인 | 명령 처리를 여러 단계로 나눠, 단계마다 다른 명령을 동시에 처리 | 앞 명령의 결과가 필요한 명령(의존성), 분기에서 멈춤 |
| 슈퍼스칼라 | 한 사이클에 여러 명령을 가져와·해석해·실행 | 동시에 실행할 수 있는 독립 명령이 충분해야 함 |
| 분기 예측 | 조건 분기의 방향을 미리 맞혀 파이프라인을 계속 채움 | 틀리면 진행한 작업을 버림 (수십 사이클 손실 가능) |
| 비순차 실행 | 준비된 명령부터 먼저 실행하고, 결과는 원래 순서대로 확정 | 재정렬 버퍼(ROB) 등 큰 회로·전력 필요 |
| 레지스터 리네이밍 | 같은 레지스터 이름을 쓰는 독립 명령을 실제로는 다른 물리 레지스터에 배정 | 물리 레지스터 파일이 커짐 |

고효율 코어(예: Cortex-A53·A55·A520 계열)는 **순차 실행**으로 회로를 작게 유지하고, 고성능 코어는 **넓은 비순차 실행**으로 IPC를 높입니다. 같은 칩 안에 두 종류를 섞는 이유가 여기에 있습니다([이기종 클러스터](../cpu/clusters.md)).

## 병렬성의 세 가지 층 { .l2 }

| 층 | 이름 | 하드웨어 | 예 |
|---|---|---|---|
| 명령 수준 | ILP | 슈퍼스칼라, 비순차 실행 | 한 스레드 안의 독립 명령 동시 실행 |
| 데이터 수준 | DLP | SIMD(NEON·SVE2), GPU, NPU | 이미지 픽셀 수천 개에 같은 연산 |
| 스레드 수준 | TLP | 멀티코어 | 앱의 UI 스레드와 렌더링 스레드를 다른 코어에서 |

??? expert "전문가 노트 — 암달의 법칙, 성능 방정식, SIMD의 실제"
    **성능 방정식.** 프로그램 실행 시간은 \(T = N_{inst} \times CPI / f\)입니다. 명령 수 \(N_{inst}\)는 ISA와 컴파일러가, 명령당 사이클 \(CPI\)(= 1/IPC)는 마이크로아키텍처와 메모리 시스템이, 클럭 \(f\)는 회로·공정·전압이 정합니다. 모바일 코어 설계는 \(f\)를 무리하게 올리면 전압이 올라가 전력이 급증하므로, IPC를 높여 같은 성능을 더 낮은 클럭·전압에서 내는 방향으로 발전해 왔습니다.

    **암달의 법칙.** 병렬화할 수 있는 비율이 \(p\)이고 코어가 \(n\)개이면 속도 향상은 \(1/((1-p) + p/n)\)입니다. \(p = 0.9\), \(n = 8\)이어도 약 **4.71배**에 그칩니다. 스마트폰 앱 대부분은 UI 스레드의 단일 스레드 성능에 크게 좌우되므로, 코어 수보다 가장 빠른 코어의 성능이 체감 속도를 정하는 경우가 많습니다. (수치는 `tools/soc_numbers.py`에서 계산)

    **SIMD의 실제.** Arm NEON은 128비트 고정 폭 벡터, SVE·SVE2는 구현마다 벡터 길이가 다를 수 있는 가변 길이 벡터 확장입니다. 현재 모바일 코어의 SVE2 구현은 128비트 폭이 일반적이어서 NEON 대비 폭 자체의 이득보다는 명령 표현력(predication, gather/scatter 등)의 이득이 큽니다. 행렬 연산은 별도 확장인 SME·SME2가 담당합니다([Arm 아키텍처](../cpu/arm-architecture.md)).

    **분기 예측 실패의 비용.** 파이프라인이 깊고 넓을수록 예측 실패 한 번에 버려지는 작업이 많아집니다. 현대 고성능 코어의 예측 실패 비용은 대략 10–20 사이클 이상이며, 그동안 넓은 코어가 처리할 수 있었던 수십 개의 명령이 사라집니다. 코어 설계가 큰 분기 예측기에 면적을 아끼지 않는 이유입니다([코어 마이크로아키텍처](../cpu/microarchitecture.md)).

## 고성능 코어 ↔ 고효율 코어 비교

| 항목 | 고성능 코어 | 고효율 코어 |
|---|---|---|
| 실행 방식 | 넓은 비순차 실행 | 순차 실행 또는 좁은 비순차 |
| 디코드 폭 | 넓음 | 좁음 |
| 캐시 | 큰 L1·L2 | 작은 L1, L2 공유하는 경우 많음 |
| 면적 | 큼 (고효율 코어의 수 배) | 작음 |
| 강점 | 단일 스레드 성능, 응답성 | 낮은 부하의 에너지 효율, 백그라운드 작업 |
