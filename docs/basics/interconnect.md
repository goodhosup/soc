# 버스와 인터커넥트

!!! spec "규격 · 세대"
    Arm AMBA (Advanced Microcontroller Bus Architecture): AMBA 2(AHB·APB) → AMBA 3(**AXI**) → AMBA 4(AXI4, **ACE** 캐시 일관성 확장, ACE-Lite) → AMBA 5(**CHI** 패킷 기반 일관성 프로토콜, AXI5) · 칩 사이·패키지 안 연결: UCIe 등 칩렛 인터페이스(논의·도입 단계)
    공유 버스 → 크로스바 → 계층형 버스 매트릭스 → 패킷 기반 **NoC(Network on Chip)**

!!! basic "한눈에 보기"
    SoC 안의 블록들은 서로 데이터를 주고받아야 합니다. CPU는 메모리를 읽고, 카메라 ISP는 사진을 메모리에 쓰고, 디스플레이 엔진은 그 사진을 읽어 화면에 보냅니다. 이 길을 **인터커넥트**라고 합니다.

    1. 초기 칩은 모두가 한 줄의 **공유 버스**를 순서대로 썼습니다. 단순하지만 한 번에 하나만 쓸 수 있습니다.
    2. 블록이 늘자 여러 쌍이 동시에 통신하는 **크로스바**로 바뀌었습니다.
    3. 지금은 데이터를 작은 **패킷**으로 나눠 도로망처럼 생긴 **NoC**로 보냅니다.

    도시에 비유하면 공유 버스는 마을에 하나뿐인 길, 크로스바는 모든 집을 잇는 직통 도로, NoC는 교차로와 신호등이 있는 도로망입니다. 도로망에는 우선순위(구급차 = 디스플레이)와 교통량 관리(QoS)가 필요합니다.

## AMBA 프로토콜 { .l2 }

| 프로토콜 | 세대 | 용도 | 특징 |
|---|---|---|---|
| APB | AMBA 2 이후 | 저속 주변장치 레지스터 접근 | 단순, 파이프라인 없음 |
| AHB | AMBA 2 | 마이크로컨트롤러급 시스템 버스 | 단일 채널, 버스트 전송 |
| **AXI** | AMBA 3 (AXI3) → AMBA 4 (AXI4) → AMBA 5 | 고성능 블록 간 데이터 전송 | 읽기·쓰기 주소·데이터·응답 **5개 채널 분리**, 다중 미해결 요청, 순서 바뀐 응답 허용 |
| **ACE** | AMBA 4 | 캐시를 가진 블록 사이의 **하드웨어 일관성** | AXI에 스누프 채널 추가 |
| ACE-Lite | AMBA 4 | 캐시 없는 블록(DMA, GPU 일부)의 일관성 참여 | 다른 캐시를 스누프하게 할 수는 있지만 자신은 스누프 대상 아님 |
| **CHI** | AMBA 5 | 대규모 일관성 인터커넥트 | 계층화된 **패킷 기반** 프로토콜, 메시·링 토폴로지에 적합 |

AXI의 5개 채널은 다음과 같습니다.

| 채널 | 방향 | 내용 |
|---|---|---|
| AR (Read Address) | 마스터 → 슬레이브 | 읽을 주소, 길이, ID |
| R (Read Data) | 슬레이브 → 마스터 | 읽은 데이터와 응답 |
| AW (Write Address) | 마스터 → 슬레이브 | 쓸 주소, 길이, ID |
| W (Write Data) | 마스터 → 슬레이브 | 쓸 데이터와 바이트 마스크 |
| B (Write Response) | 슬레이브 → 마스터 | 쓰기 완료 응답 |

## 크로스바에서 NoC로 { .l2 }

| 구조 | 장점 | 한계 |
|---|---|---|
| 공유 버스 | 배선 적음, 단순 | 동시 통신 불가, 블록이 늘면 병목 |
| 크로스바 | 여러 쌍이 동시에 통신 | 포트 수의 제곱으로 배선·면적 증가, 물리 배치 어려움 |
| **NoC** | 패킷을 라우터로 전달, 확장성·물리 배치 유리, QoS 정책 적용 쉬움 | 패킷화·라우팅 지연, 설계 도구 필요 |

현대 모바일 SoC는 보통 두 층으로 나뉩니다. CPU 클러스터·GPU처럼 **캐시 일관성이 필요한 블록**은 일관성 인터커넥트(ACE·CHI 기반)로, ISP·코덱·디스플레이처럼 **대용량 데이터를 흘리는 블록**은 비일관성 NoC로 묶고, 두 영역이 SLC와 메모리 컨트롤러 앞에서 만납니다.

??? expert "전문가 노트 — QoS, 실시간 블록, 보안 속성, 상용 NoC IP"
    **QoS가 SoC 성능을 정한다.** 디스플레이 엔진은 매 프레임 정해진 시간 안에 픽셀을 읽지 못하면 화면이 깨집니다(underflow). 카메라 ISP도 센서가 데이터를 계속 밀어 넣으므로 쓰기가 막히면 프레임을 잃습니다. 이런 **실시간(isochronous) 트래픽**은 CPU·GPU 같은 최선 노력(best-effort) 트래픽보다 높은 우선순위와 대역폭 보장을 받아야 합니다. NoC와 메모리 컨트롤러는 마스터별 우선순위, 대역폭 상한(regulation), 버퍼가 차오를 때 우선순위를 올리는 위급도(urgency) 신호 등을 씁니다. "게임 중 카메라를 켜면 프레임이 떨어진다" 같은 현상의 원인이 여기에 있는 경우가 많습니다.

    **보안 속성이 버스를 따라간다.** AXI 트랜잭션에는 보안·비보안 여부를 나타내는 속성(AxPROT의 NS 비트)이 실려 다니며, 인터커넥트와 메모리 방화벽(TZC 같은 주소 공간 제어기)이 이를 검사해 일반 세계에서 보안 메모리로의 접근을 막습니다. TrustZone이 CPU만의 기능이 아니라 **버스 전체의 기능**인 이유입니다([TrustZone과 TEE](../security/trustzone.md)).

    **상용 NoC IP.** NoC는 직접 만들기도 하지만, Arm CoreLink 인터커넥트나 Arteris 같은 회사의 NoC IP를 많이 씁니다. 설계자는 마스터·슬레이브 목록, 대역폭 요구, 클럭·파워 도메인, 물리 배치를 입력하고 도구로 토폴로지를 생성·검증합니다([IP와 통합](../design/ip-integration.md)).

    **일관성의 비용.** 일관성 인터커넥트는 다른 블록의 캐시를 스누프해야 하므로 트래픽과 지연이 늘어납니다. 그래서 모든 블록을 일관성 영역에 넣지 않고, 필요한 블록만 ACE-Lite·I/O 일관성으로 참여시키거나 소프트웨어가 캐시를 직접 비우게(cache maintenance) 합니다([캐시와 일관성](../cpu/cache-coherence.md)).

|---|---|---|
| CPU 클러스터 연결 | DSU → CHI 기반 인터커넥트 | 자체 클러스터 패브릭 |

| 공개 정보 | Arm 공개 문서로 프로토콜 확인 가능 | 공개 분석·특허 위주 |
