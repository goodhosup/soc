# 메모리 컨트롤러와 SLC

!!! spec "규격 · 세대"
    메모리 컨트롤러·SLC 구조는 회사별 설계 · 외부 인터페이스: JEDEC LPDDR, 내부: AMBA AXI·CHI · Linux 측: interconnect 프레임워크(대역폭 투표), devfreq(메모리 주파수), Qualcomm 계열은 시스템 캐시 드라이버(`drivers/soc/qcom/llcc-qcom.c`)로 SLC 영역 관리
    CPU 전용 캐시만 존재 → 클러스터 공유 L3 → **SoC 전체가 공유하는 SLC**(블록별 영역 분할, 소프트웨어 제어)

!!! basic "한눈에 보기"
    DRAM 앞에는 두 명의 관리자가 있습니다.

    1. **메모리 컨트롤러** — CPU·GPU·NPU·ISP·디스플레이가 동시에 보내는 수많은 읽기·쓰기 요청을 받아, DRAM이 가장 효율적으로 처리할 수 있는 순서로 바꿔 보냅니다. 급한 요청(화면 표시)은 먼저 처리합니다.
    2. **SLC(System Level Cache)** — 메모리 컨트롤러 바로 앞의 큰 공유 캐시입니다. 여러 블록이 자주 쓰는 데이터를 칩 안에 붙잡아 두어, 느리고 전력을 많이 쓰는 DRAM까지 가는 횟수를 줄입니다.

    공항에 비유하면 메모리 컨트롤러는 활주로 관제탑(이착륙 순서 조정, 응급 항공기 우선), SLC는 공항 안의 환승 라운지(밖으로 나가지 않고 갈아탈 수 있게)입니다.

## 메모리 컨트롤러가 하는 일 { .l2 }

| 기능 | 내용 | 목적 |
|---|---|---|
| 요청 재정렬 | 같은 행(row)에 대한 요청을 모으고, 읽기·쓰기를 묶어 전환 횟수를 줄임 | DRAM 효율 (row hit 증가) |
| 뱅크 병렬화 | 여러 뱅크에 요청을 나눠 동시에 진행 | 지연 숨김 |
| QoS 우선순위 | 디스플레이·카메라 같은 실시간 요청 우선, 대역폭 상한 적용 | 화면 끊김·프레임 손실 방지 |
| 리프레시 관리 | 리프레시를 덜 바쁜 시점에 배치 | 성능 손실 최소화 |
| 주소 매핑 | 물리 주소를 채널·뱅크·행·열로 분산 | 접근을 고르게 퍼뜨림 |
| 트레이닝 | 부팅·주파수 전환 시 신호 타이밍 보정 | 고속 링크 안정성 |
| 전력 관리 | 유휴 채널 절전, 셀프 리프레시 진입, DRAM 주파수 전환 | 대기 전력 |

## SLC의 역할 { .l2 }

| 쓰임 | 효과 |
|---|---|
| CPU의 마지막 캐시 | L2·L3를 넘친 데이터를 DRAM보다 빠르게 공급 |
| GPU 렌더링 | 텍스처·프레임 버퍼 일부를 칩 안에 유지 → DRAM 트래픽 감소 |
| 디스플레이 | 정지 화면 프레임을 SLC에 두면 DRAM을 깨우지 않고 화면 갱신 가능 |
| NPU | 중간 결과·가중치 일부를 붙잡아 재사용 |
| 모뎀·DSP | 저전력 상시 작업이 DRAM을 깨우지 않도록 |
| 블록 간 데이터 전달 | ISP가 쓴 데이터를 GPU·NPU가 SLC에서 바로 읽음 |

SLC는 모든 블록이 공유하므로, 한 블록이 독차지하면 다른 블록이 손해를 봅니다. 그래서 SLC를 **블록별 영역(slice, partition)으로 나누고**, 소프트웨어가 사용 상황(예: 카메라 촬영 중, 게임 중)에 따라 영역 크기와 우선순위를 바꾸는 구조가 쓰입니다.

??? expert "전문가 노트 — SLC는 성능보다 전력, QoS의 실제, 대역폭 투표"
    **SLC는 전력 장치다.** SLC의 가장 큰 이득은 종종 성능보다 **DRAM 접근 에너지 절감**입니다. 비트당 에너지로 보면 칩 밖 DRAM 접근은 칩 안 SRAM 접근보다 훨씬 비싸므로, 같은 데이터를 여러 번 읽는 작업에서 SLC 적중은 곧 배터리 절감입니다. 정지 화면이나 저부하 상태에서 DRAM을 셀프 리프레시에 둔 채 SLC만으로 작업을 처리하는 시나리오가 대표적입니다.

    **QoS의 실제.** 메모리 컨트롤러의 스케줄러는 단순히 처리량을 최대화하면 안 됩니다. 디스플레이 엔진이 버퍼 부족 위험을 알리면(위급도 신호) 그 요청을 가장 먼저 처리하고, CPU·GPU의 최선 노력 요청은 뒤로 미룹니다. 반대로 CPU 지연에 민감한 요청을 GPU의 대량 스트림이 밀어내지 않도록 마스터별 대역폭 조절도 필요합니다. 이 정책은 SoC마다 크게 달라, 같은 DRAM을 써도 "게임 중 앱 전환 반응성" 같은 체감이 달라집니다.

    **대역폭 투표.** Android 커널에서 각 드라이버는 자신이 필요한 메모리·버스 대역폭을 interconnect 프레임워크에 "투표"하고, 이를 합산해 버스·DRAM 주파수가 정해지는 구조가 흔합니다. 드라이버가 필요 이상으로 투표하면 DRAM이 높은 주파수에 머물러 전력이 새고, 부족하게 투표하면 화면 끊김이 생깁니다. 전력 문제를 분석할 때 DRAM 주파수 트레이스(devfreq)와 투표 내역을 함께 보는 이유입니다([전력 측정과 분석](../power/measurement.md)).

    **주소 인터리빙.** 연속된 주소가 한 채널에만 몰리면 대역폭을 다 쓰지 못하므로, 물리 주소의 일부 비트를 해시해 채널·뱅크를 고르게 섞습니다. 이 해시 때문에 "특정 간격으로 접근하는 코드"의 성능이 칩마다 다르게 나오기도 합니다.
